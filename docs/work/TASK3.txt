У практиках 1–2 обчислювальний код запускався напряму на хості, що створювало залежність від версій бібліотек («на моєму комп'ютері працює») та не захищало систему від вичерпання ресурсів ненажерливими процесами.

Мета роботи:
1. Запакувати обчислювальний бекенд у відтворюваний та безпечний Docker-образ.
2. Налаштувати декларативну мультиконтейнерну оркестрацію через `docker-compose.yml`.
3. Дослідити поведінку системи під лімітами cgroups v2 (CPU throttling, OOMKilled) та зафіксувати накладні витрати віртуалізації ядра (Bare-Metal vs Docker).

Що потрібно виконати (Покроковий план)

1. Складання продакшн-орієнтованого `Dockerfile`
Створіть `Dockerfile` для вашого сервісу (реактор Монте-Карло або проєкт енергомережі IEEE-118), реалізувавши ключові інженерні вимоги:
* Базовий образ: `python:3.11-slim` (використання Debian `glibc` для швидкого встановлення wheel-пакетів замість важкої компіляції під Alpine `musl`).
* Оптимізація кешування: інсталяція `requirements.txt` виконується до копіювання коду застосунку (`COPY requirements.txt .` -> `RUN pip ...` -> `COPY app.py .`).
* Безпека: створення та запуск під непривілейованим користувачем (`USER appuser`, UID 10001) для запобігання Container Escape.
* Graceful Shutdown: exec-форма точки входу `ENTRYPOINT ["python", "app.py"]` без запуску проміжної оболонки `/bin/sh -c`, щоб передавати `SIGTERM` безпосередньо процесу на `PID 1`.
* Healthcheck: перевірка доступності ендпоінта `/api/health`.

2. Конфігурація `docker-compose.yml`
Опишіть маніфест запуску комплексу:
* Прокидання портів: відкриття `8080:8080` (мапінг зовнішнього інтерфейсу на ізольований `net` namespace).
* Жорсткі ліміти cgroups:
* CPU: квота `cpus: "2.00"` (200 мс процесорного часу на кожні 100 мс інтервалу планувальника).
* Memory: ліміт `memory: 512M` (захист хоста від неконтрольованого розростання пам'яті).
* Мережа: використання ізольованої підмережі мостового типу (`driver: bridge`).

3. Інженерні експерименти (Обов'язкова частина звіту)
Проведіть три випробування та зафіксуйте результати:
1. CPU Throttling: запустіть пакетний прогін симуляції (`POST /api/batch`), одночасно відстежуючи метрики у терміналі через `docker stats`. Зафіксуйте граничне значення утилізації CPU та факт тротлінгу.
2. OOMKilled (Exit Code 137): запустіть тестовий контейнер з критично малим обсягом пам'яті (`--memory=64m`) та спровокуйте навантаження. Зафіксуйте вимушене завершення процесу ядром за сигналом `SIGKILL` (код завершення `137`).
3. Бенчмарк Bare-Metal vs Docker: виконайте однаковий прогін 20 кроків симуляції на голому залізі хоста та всередині контейнера. Зафіксуйте різницю в часі виконання (оверхед контейнеризації).

Формат здачі

У репозиторії мають бути:
1. Код бекенду з REST API (`/api/health`, `/api/step`, `/api/batch`, `/api/metrics`) та веб-інтерфейсом.
2. `Dockerfile` та `docker-compose.yml`, що запускають сервіс однією командою: `docker compose up --build`.
3. Файл звіту або нотаток (`BENCHMARK.md` або `DECISIONS.md`), який містить:
* скріншоти або термінальні логи роботи `docker stats` під навантаженням;
* підтвердження коду `Exit Code 137` при OOMKilled;
* підсумкову порівняльну таблицю швидкодії: Bare-Metal (сек) vs Docker (сек).
