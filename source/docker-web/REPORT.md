# Звіт — етап 3, Docker, IEEE-118

Сервіс: `ieee118-sim-service`, образ `my-grid-lab/ieee118-sim:stage3`. Код: `source/docker-web/`.

Прогін часу: `s = 83810`, `seed = 42`, `--shock weighted`, `--unrated-margin 2.0`, `--threshold 0.05`, `--trials 10000 --k 1`. Таймер стартує після створення пулу (`time_includes_pool_startup: false`).

## 1. Квота CPU і пам’яті сервісу

Compose тримає стелю `cpus: "2.00"` і `memory: 512M`. У `docker stats` стовпчик `CPU %` рахує одне ядро як 100%, тож стеля двох ядер — близько 200%. Пам’ять у кадрі ділиться на 512 МіБ.

Два кадри `ieee118-sim-service` (`cpu-throttle.png`, `cpu-throttle1.png`):

| Кадр | CPU % | MEM USAGE / LIMIT | MEM % | PIDS |
| :--- | ---: | :--- | ---: | ---: |
| 1 | 113.42 | 88.38 МіБ / 512 МіБ | 17.26 | 8 |
| 2 | 56.00 | 93.58 МіБ / 512 МіБ | 18.28 | 8 |

Обидва кадри нижче стелі 200% і далеко від 512 МіБ: процес живий, пам’ять тримається біля 90 МіБ. CPU для цього ліміту стискається планувальником. Поки контейнер у межах квоти, він лишається `Up` і не втрачає стан сесії. Ці кадри фіксують роботу під лімітом, а не упирання в 200%.

## 2. OOM, 44 МіБ

Окремий контейнер, не сервіс Compose. Ліміт пам’яті тут спеціально `44m`, не 512 МіБ сервісу і не 64 МіБ з чернетки плану:

```powershell
docker run --rm --memory=44m --name ieee118-oom -p 8081:8080 `
  -e DATA_DIR=/data -e SCRIPT_DIR=/scripts -e SIM_WORKERS=4 `
  -v "...\dataset_cascades:/data:ro" `
  -v "...\dataset_scripts:/scripts:ro" `
  my-grid-lab/ieee118-sim:stage3
echo $LASTEXITCODE
```

Лог (`oom-killed.png`) встигає надрукувати `loaded scenario s=83810 once`, банер сервера, `Workers: 4` і `PID: 1`. Після цього процес зникає. `$LASTEXITCODE` дорівнює **137** (`128 + 9`, `SIGKILL` від OOM killer).

44 МіБ вистачило на імпорт, читання одного сценарію і старт пулу. Наступної сторінки ядро вже не дало. Інтерпретатор не встиг кинути `MemoryError`: стан процесу обірвано. Сервіс на 512 МіБ цей пробник не чіпає.

## 3. Bare-metal і Docker, один і той самий рахунок

Джерела: `bench-out/benchmark_results_host.json` і `bench-out/benchmark_results_docker_free.json`.

Обидва прогони без квоти `cpus: "2.00"`. Такого заміру немає. В обох JSON `cpu_count` дорівнює 20: хост і контейнер бачать одні й ті самі 20 ядер. Файл `benchmark_results_docker_web.json` у таблицю не входить: там `k = 2` і інший набір воркерів.

`deterministic_across_workers` в обох файлах `true`. `P(blackout) = 0`, `cascade_fraction = 0`. `mean_dns_proxy` дорівнює `6.431682344513676e-05` на хості і `6.431682344513677e-05` у контейнері: розходження в останньому біті суми. Число ударів `in_shock` по гілках збігається. Швидший рядок рахує ті самі 10 000 випробувань.

| Воркери | Bare-metal, с | Docker, с | Docker / host | Trials/s, host | Trials/s, Docker |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.441 | 0.402 | 0.91 | 22 656 | 24 850 |
| 2 | 0.283 | 0.195 | 0.69 | 35 299 | 51 394 |
| 4 | 0.145 | 0.107 | 0.74 | 69 081 | 93 360 |

| Воркери | Speedup, host | Speedup, Docker | Ефективність, host | Ефективність, Docker |
| :--- | ---: | ---: | ---: | ---: |
| 1 | 1.00 | 1.00 | 1.00 | 1.00 |
| 2 | 1.56 | 2.07 | 0.78 | 1.03 |
| 4 | 3.05 | 3.76 | 0.76 | 0.94 |

Контейнер швидший на кожному рядку: на 1 воркері приблизно на 9%, на 2 — на 31%, на 4 — на 26%. Квота з §1 тут ні до чого: обидва прогони йшли на 20 видимих ядрах.

Один воркер пул не створює: цикл іде в батьківському процесі. Різниця 0.441 с проти 0.402 с — це інтерпретатор і ОС. Хост лабораторії — Windows, поруч у каталозі лежить байткод `cpython-314`. Образ — `python:3.11-slim` на Linux. JSON версію інтерпретатора не записує.

На 2 і 4 воркерах розрив ширший за рядок одного воркера. До різниці інтерпретаторів додається спосіб запуску процесів. На Windows `Pool` працює через `spawn`: кожен воркер — новий інтерпретатор, чанк і відповідь їдуть через IPC. У Linux 3.11 метод за замовчуванням — `fork`: воркер отримує топологію через `initializer` і ділить сторінки батька. У час `time_s` старт пулу не входить, але `pool.map` на цих двох шляхах коштує по-різному. Сам граф тут малий: `topology_pickle_bytes` дорівнює 9021, файл `.mat` читається один раз до таймера.

Чотири воркери при `cpu_count` 20 у стелю ядер не впираються. Тому speedup до 4 ще росте: 3.05 на хості і 3.76 у контейнері. Ефективність Docker на двох воркерах виходить 1.03, частка Амдала від’ємна. Прогін триває 0.1–0.4 с і знятий один раз. Це шум короткого заміру, а не від’ємна послідовна частка алгоритму. Напрямок однаковий у всіх трьох рядках, тож висновок не тримається на одному викиді.
